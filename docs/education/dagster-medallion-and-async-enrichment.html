Read this first: the inventory metaphor

Think of the warehouse pipeline as inventory management for a shop. We "stock" tables (assets). We can only stock a shelf if the shelf it depends on is stocked first. Most restocking runs on a clock. Some restocking happens when a delivery truck arrives — an event we can't predict, so we keep an eye out for it. Every Dagster term below maps onto that picture.

1 · The Dagster primitives

Dagster has a small vocabulary. Each idea is simple; the power comes from combining them.

Asset — the thing we stock

An asset is a persistent object our code produces — usually a table. Assets are nouns: silver_ig_posts, gold_growth_facets, a serving view.

One asset = one node

Asset dependency — "you can't stock X until Y"

Assets link into a graph: an edge means the downstream asset needs the upstream one to exist first. Serving depends on gold; gold depends on silver.

A tiny graph
The everyday image

The "shelf with weekly metrics" can't be filled until the "clean post table" shelf is filled. Dagster just tracks these edges and runs things in the right order.

Job, schedule, sensor, partition

The four "when/how" controls
Quick reference. Job = what to run together. Schedule = run it on a clock. Sensor = run it when something external happens. Partition = run/backfill a slice. Asset checks/freshness = quality gates and "how stale is this?" — we use them to fail loudly on bad/wedged data.

2 · The canonical medallion pattern

Our data warehouse is layered like most: bronze → silver → gold → serving → dashboard. Each layer is a set of assets; the next depends on the previous.

The standard layered medallion graph
The hidden assumption. A normal medallion transform is fast and synchronous — materializing gold is a normal compute step taking seconds to minutes. That premise is true for cleaning data. It is false for the next thing we do, which is why the next section exists.

3 · Where we depart: async AI enrichment

This section describes the engine as it runs TODAY. The (post_id, domain) MERGE key and the table names shown here are the current implementation. ADR-0011 replaces the join key with platform and moves the conformed tables to silver_*; see section 8 for the target.

We also want to enrich each post with an AI model that reads its media — detect the brand logos, whether a face is present, the "value medium", and (soon) transcribe the audio. Three facts make this unlike a normal transform:

  • Slow — enriching a whole corpus takes hours (one big pass ≈ 15 hours), not seconds.
  • External — it calls a network API (an LLM batch service).
  • Per-record — every post is a separate model call.

If we modelled this as a normal synchronous asset step, a materialization would block for 15 hours and re-run everything naively. That breaks the fast-and-synchronous assumption of section 2.

Our answer: an async bridge. The enrichment stays in the asset graph but is split so Dagster never waits. Sub-second submit + an external service that drains in its own worker + a sensor that harvests each completed batch.
The async enrichment bridge
Beginner-trap correction: new posts reaching silver trigger the submit via asset dependency (silver → submit) — not a sensor "watching" for posts. Sensors are only the async completion bridge, polling the external service.

One post → several enrichment dimensions

A single post is enriched by several independent services, each writing its own gold table:

  • facets (LLM reads media) → gold_growth_facets
  • transcripts (whisper transcribes audio) → silver_audio_transcripts (target name; the never-built gold_transcripts predates ADR-0011 — see section 8)

So "done" is per-dimension, never a single enriched = True boolean — we can't know which upstream consumer needs which dimension. Each post has a status per dimension: pending / in-flight / done / failed / stale.

Fan-out, independent work, rejoin at serving

5 · The scheduling mental model

Because enrichment is post-driven (a post is done when it has a current gold row), it isn't really a clock-based pipeline. We schedule different parts differently — all under one orchestrator (Dagster):

Different parts, different triggers — one orchestrator
Initial load vs. daily? For time-series core assets (silver/serving by period) we use partitions + a schedule, and a full historical load is a partition backfill. For post-driven enrichment, partitions don't fit: a post is done by state (current gold row), so a full re-run is just a manually-launched job — a model/prompt change auto-re-enqueues everything that's now stale. No second partition system needed.

6 · Decision cheat-sheet

Reach for…WhenOur usage
SchedulePredictable, recurring work on a clockHourly fast core; optional nightly publish
Asset dependencyDownstream can run only after upstream (ordering). To auto-run downstream on new upstream data, wire a declarative automation condition (eager / on_new_upstream_data) or a sensor — the edge alone schedules nothingsilver → enrichment submit (new posts)
SensorReact to an external event Dagster can't foreseeservice job completes → trigger harvest
JobA named selection to launch together, incl. one-off / full runsfull_corpus_enrichment re-run
PartitionSplit a time-series asset for incremental / backfillcore silver/serving by period (not gold)
Takeaway: schedule the fast core · asset-dependency the submit · sensor the async completion · manual job the full re-run. Keep the async services as external backends, and enrichment stays in the graph without ever blocking it.

7 · Dev / test playbooks

Because the enrichment engine is a CLI driver over file-based DuckDB + an external service, a "test environment" is just the same code pointed at scratch databases — no special environment needed, and a tiny real run costs a fraction of a cent. The driver already exposes every knob you need: --plan (offline dry-run, no spend), --limit, --posts, --state-db, --ops-db, --service-url, --mode.

The one rule: never let a test run write to the real data/state.duckdb or data/ops.sqlite. Copy them to a scratch dir first. The engine also reads media by absolute path from the same machine — so scratch runs can safely read the real data/media/posts byte cache read-only.
An isolated test workspace = same code, scratch DBs

Playbook A — plan a subset with no spend (dry-run)

# one-time: fresh scratch copies (real silver + media_cache come along)
mkdir -p data/dev
cp data/state.duckdb data/dev/state_dev.duckdb
cp data/ops.sqlite  data/dev/ops_dev.sqlite

# offline: show what 20 visual targets WOULD submit — nothing submitted, $0
# (--plan also creates the empty gold table in the scratch DB if missing — harmless)
uv run python scripts/enrich_facets_batch.py --plan --mode visual \
  --limit 20 --state-db data/dev/state_dev.duckdb --ops-db data/dev/ops_dev.sqlite

Playbook D — fake N "new posts" and see how the pipeline treats them

The engine discovers posts from silver_ig_posts. To simulate new arrivals, insert synthetic rows into the scratch silver. Two gotchas: the done-guard skips a fake whose post_id collides with a real gold row (use fresh ids), and visual mode needs cached media — a URL with no cached bytes is skipped. The reliable way to give a fake media is to reuse a real post's already-cached media, not to invent a URL (see the note below for inventing one).

# Recommended — reuse real, cached media so visual mode resolves bytes.
# The scratch db is a full copy, so a REAL post that isn't yet in gold is
# already a perfect "new arrival": no synthetic row needed.
#   1) pick a real visual post not yet enriched
#      (it is NOT in gold_growth_facets):
SELECT post_id FROM silver_ig_posts
WHERE caption <> '' AND media_files NOT IN ('[]')
  AND post_id NOT IN (SELECT post_id FROM gold_growth_facets) LIMIT 5;

#   2) run it exactly like a brand-new post (Playbook C against scratch):
uv run python scripts/enrich_facets_batch.py --run --mode visual \
  --posts 3691893705957994148 \
  --state-db data/dev/state_dev.duckdb --ops-db data/dev/ops_dev.sqlite

# Want a genuinely NEW fake id instead? Clone a real cached post's row under
# a fresh post_id (its media_files URL is already in the media cache, so
# media_paths finds the bytes). DuckDB lets you copy then override:
INSERT INTO silver_ig_posts
SELECT * REPLACE ('9990000000000000001' AS post_id)
FROM silver_ig_posts WHERE post_id = '3691893705957994148';

# Note on inventing a URL: media_paths looks up media_cache by
# sha256(url), so a made-up URL resolves ONLY if you add a row whose
# cache_key = sha256(url) hexdigest pointing at a file that exists on disk.
# Reusing a real cached post's URL sidesteps all of that.

Then run Playbook C's --run --posts 9990000000000000001 (or --limit N) against the scratch DB and watch the gold row appear for your fake. Delete the scratch dir when done.

And "test versions of the asset graph"? Today the enrichment isn't in the Dagster graph — it's the CLI driver — so today the subset and the isolation are the same knob: --posts/--limit pick which posts run, and --state-db/--ops-db point writes at a scratch DB. When we fold enrichment into Dagster, keep those two ideas separate and reach for the three mechanisms you'll actually meet: (1) isolation — point the resources at scratch paths via env-var config (OPS_DB_PATH / IG_DATA_DIR already exist here; one .env per environment); (2) subset — asset selection, not the DB (materialize just gold_growth_facets + its downstream(), or one partition); (3) unit tests — call materialize() in pytest with the same resources on scratch paths (test_facets_batch.py already does). No special test code-location required.

8 · The v3 target: layered enrichment and Dagster-native orchestration

Everything above describes the engine as it runs today. Two accepted decisions change where its state and its tables live. Neither is built yet — read this as the destination, not the map.

Accepted, not implemented. ADR-0011 and ADR-0012 are ratified decisions dated 2026-09-10. The code still runs the model described in sections 1–7: enrichment is a CLI driver over ops.sqlite, gold tables are per-channel mirrors, and no model response is landed verbatim.

ADR-0011 — the layered model

The enrichment outputs stop being gold mirrors and become a strict medallion chain of their own. Verbatim model responses land in bronze_enrichment_raw (immutable, Parquet, keyed (post_id, platform, workload, prompt_hash, run_id)). Six silver_* tables are conformed from it deterministically, with zero API calls. Four gold marts join them to the canonical metric views.

The payoff is economic: because the raw response is landed, a schema or mapping change is a replay of silver rather than a re-call of the paid model. Today nothing is landed — both paths parse the response in flight and discard it, so every schema change re-buys the corpus.

Two rules matter most for anyone extending this: the join key is platform and never domain (domain means the content niche; today's gold_analyses.domain holds 'instagram', a platform — the duplicate-name bug), and validation lives in silver, not in the write path of a paid table.

ADR-0012 — orchestration is Dagster-native

Orchestration state moves out of ops.sqlite and into the Dagster instance and the lake. The queue tables (batch_jobs, batch_items, dead_letter) and facets_batch_jobs are retired. ops.sqlite keeps only what has no Dagster equivalent: media_cache, media_metadata, creators, profiles, creator_merges, prompt_registry.

Two consequences worth knowing before you build on the current design. Retry becomes a new partition key rather than a mutable status column. And the discovery drain (ig_posts_gen_batches) loses its in-flight guard, which today reads batch_items WHERE status IN ('pending','processing') — it must derive in-flight state from the Dagster instance instead, or it double-submits paid work.

The inference service and the swap seam

One seam serves every workload: a shared ledger plus three verbs — submit, poll-to-terminal, retrieve. (harvest is our step that composes poll and retrieve with an idempotent landing; it is not a seam verb.)

The point of the seam is that the provider becomes swappable: a ProviderAdapter with one canonical state vocabulary, implemented by a ServiceBackedAdapter (the qwen-batch service) and a DirectBatchAdapter (Gemini-shaped). build_adapter(name) is the only place a provider is named.

The subtlety that makes one seam cover both: OpenRouter/qwen is synchronous — it answers in-request and holds nothing server-side — while Gemini batch is natively async. The qwen-batch service exists to make the synchronous provider behave asynchronously, and the adapter absorbs that difference so nothing downstream knows which provider ran.
