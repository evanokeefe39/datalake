## 2. Missed industry patterns (data-specific)

It never names the enforcement mechanism: a declared contract with a consumer-side test that fails when the producer's schema or output vanishes. The `test_state_compatibility.py` fiasco is the negative proof — a test asserting status quo is what you get without a contract that expects the NEW world. The post-mortem treats this as one silent-failure bullet. The stronger statement: this pipeline currently has **no DQ gate capable of failing** (see F6). Whether Dagster-native checks or dbt-duckdb tests — the gate must exist and must fail on plausible corruption; the tool choice is hindsight-adjacent, the absence is not. |

## 3. The read-side/write-side asymmetry — the standard control

The central defect (producer with no consumer; consumer with no producer) is prevented, in data engineering, by a **declared lineage contract with an orphan check**: every materialized asset declares its upstream inputs AND its downstream consumers, and a gate fails if any declared output has zero consumers or any consumer reads a source with zero producers. Not a unit test — a **pipeline-manifest/lineage assertion** (in Dagster terms: the asset `deps` graph plus a blocking integration check; in dbt terms: the manifest's exposure/parent lists plus a "no orphan model" audit; in contract terms: a schema-registry entry naming consumers, violated when the consumer's expected input stops arriving).

Which the design HAD and failed to use:

- The master plan's §4 blast-radius register **is** a static lineage manifest — it names `ig_posts_gen_batches` as Phase 2's consumer and the drain as the load-bearing cross-phase dependency. The information to prevent defect #1 was written down before any dispatch.
- What it lacked: (i) the register was never converted into **runtime lineage** — the Dagster asset graph contains no edge making submit a consumer of the drain's partitions, so nothing structural could fail; (ii) the register was never converted into **per-dispatch acceptance questions** ("name the production consumer of what you write") — the post-mortem's §8.5 says this correctly but does not recognize that the register was the manifest that should have generated those questions automatically; (iii) no orphan check — "twelve objects exist only as code" and "zero views read `silver_content_classification`" are exactly what an orphan-consumer / orphan-producer lineage audit enumerates in one pass.

So the precise answer: it is a **manifest-into-lineage-control** failure, not a unit-test failure and not a "contract" in the vague sense — the contract document existed (§4), the enforcement mechanism (asset-graph dependency + orphan assertion) did not.

## 4. Seams-owner vs producer/consumer — the DATA lens decision

**They are distinct; the post-mortem treats them as one learning. The separating axis is static interface topology vs runtime data topology.**

- **"Seams need owners"** is about *code topology*: for every abstraction boundary (the provider seam, the handle format, the partition-key shape), exactly one party has authority to define and change it, and adopters conform. It is decided at design/dispatch time, and its failure mode is divergence (two encodings, two HTTP clients, two terminal predicates — defects #5, #6, #13).
- **Producer/consumer checks** are about *data flow at runtime*: every written artifact has a named production consumer; every read source has a named production producer, and the pairing is demonstrated firing (a materialization observed). It is verified at acceptance, and its failure mode is orphaning (defects #1, #2, the callerless conform).
- They are related (a seam is itself a producer/consumer pair of interfaces) but orthogonal: here the seam had one adoption and a defined owner yet the harvested producer went unassigned (seam owned, flow orphaned); conversely drain and submit both existed with clear module ownership while their data handoff existed in no graph (owners named, flow disconnected).

Correction to the post-mortem: it should carry these as **two** remediations — (1) dispatch must name the seam owner and enumerate adopters; (2) acceptance must demonstrate producer/consumer firing. Collapsing them into one "give each contract an owner" produces fixes like more docstrings, when the producer-consumer half needs an integration run and an orphan audit.

## 5. Verdict: "architecture is sound, implementation drifted"

**Unfair as stated — the correct split is: the layered model (ADR-0011) is sound and drifted; the orchestration semantics (ADR-0012) are underspecified, which is a design gap, not an implementation gap.**

Test the three named omissions against the ADRs:

1. **Retry driver.** ADR-0012 defines the retry *mechanism* (round keys, distinctness) and the master plan has zero matches for retry/attempt/backoff; no ADR names the actor who mints round N or decrements the failed-submit counter. A mechanism with no driver is not "sound architecture awaiting implementation" — it is an incomplete specification. **Design gap.** The round-0 double-submit (defect #7) is its direct consequence: you cannot implement a driver for an actor the design never named, and the worker correctly implemented the only case the spec fully determined (round 0).
2. **Quarantine consumer.** `silver_enrichment_quarantine` is designed as a table with an explicit rule ("unparseable → quarantine loudly") and **no declared consumer, disposition policy, or SLA** anywhere in the ADRs or plan. A quarantine table nobody reads is a dead-letter queue without a redrive policy — a design omission, not an implementation lapse. **Design gap.**
3. **Harvested producer.** review-architecture §1 calls the in-flight state "complete in the design" — and it is, *as a set expression* (`submitted ∖ harvested`). But a set expression is not a producer: no ADR or plan names the asset/job that materializes `enrichment_harvested` or when it fires. The design specified a *state derivation* and omitted the *state transition event* that keeps the derivation truthful. **Design gap.**

The pattern across all three: the ADRs are precise about **statics** (layers, keys, seams, verbatim landing, deterministic conform) and silent about **dynamics** (who fires, who consumes, who redrives, what freshness means). An underspecified dynamic surfaces as exactly the observed "implementation drift" — every dynamic omission became a missing writer, a missing driver, or a disconnected half that no worker's slice could reveal.

So the fair verdict is three-way, and the post-mortem's two-way split is itself a drift:

- **ADR-0011 (layering, seam, medallion): sound.** Implementation drifted (bypass sites, zombie contracts) — orchestration's fault, as argued.
- **ADR-0012 (orchestration semantics): underspecified.** Retry driver, quarantine consumer, harvested producer are design gaps that would have existed under any dispatch quality; the master plan converting known cross-phase couplings into per-phase checkboxes amplified but did not originate them.
- **The acceptance instrument: the true dominant cause, as the post-mortem says** — but add that no data-side gate (orphan lineage check, freshness/volume assertion, parallel-run diff) existed at ANY level, orchestrator or worker, so the data defects were invisible by construction, not just by decomposition.

**Bottom line:** "architecture sound / implementation drifted" fails falsification for ADR-0012. The migration's data architecture was sound where it was specified and silent where it mattered most (dynamics, lineage, DQ, freshness). The post-mortem should say: *sound statics, underspecified dynamics, unimplemented everything, accepted by vacuous gates.*
