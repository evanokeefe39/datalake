# Review: partition-key round semantics and the double-submit guard (round semantics)

- Scope: `src/datalake/defs/enrichment/partitions.py`, `src/datalake/defs/instagram/assets.py`, ADR-0012/0013.
- Verdict summary: the alleged double-submit mechanism is **REAL as a conditional** — it fires the moment a retry mints a round-N>0 key, which ADR-0012 decision 5 mandates and which nothing in the drain can see. It is **latent, not live today**: no code path in the repo yet materializes a round-N>0 key (retry still runs on the legacy `batch_items` queue; see §1). The structural cause (unscannable digest) is real and is the reason the guard cannot be made correct without an interface decision.
- Recommended fix: option (a) — the guard scans rounds `0..MAX_ATTEMPTS`. One code change, no ADR amendment, no key-shape change. Details in §3.

---

## 1. Mechanism verdict: REAL (conditional — latent until retry lands on the new key scheme)

Code paths, with line evidence:

- `partitions.partition_key(workload, attempt_round, post_ids)` — `partitions.py:118-156`. Payload is `"\x00".join([workload, str(attempt_round), *ids])` hashed to `sha256(...)[:16]` (`partitions.py:155-156`). The round is fused into the digest; the output is a one-way 16-hex-char string.
- `partitions.in_flight_partitions(instance)` — `partitions.py:205-236`: `return submitted - harvested` (`partitions.py:236`) over ALL materialized partition keys of `enrichment_submitted` / `enrichment_harvested` (`partitions.py:229-235`). No round filter — the set spans every round.
- `DRAIN_ATTEMPT_ROUND: int = 0` — `assets.py:1026-1028`.
- `drain_suppressed_post_ids(candidates, instance)` — `assets.py:1043-1061`: suppression test is exactly `partition_key(DRAIN_WORKLOAD, DRAIN_ATTEMPT_ROUND, [pid]) in keys` (`assets.py:1056-1061`). It can only ever construct the **round-0** key.
- `_materialize_submitted_partitions(instance, post_ids)` — `assets.py:1064-1087`: materializes the same round-0 keys (`assets.py:1083-1087`) after the guard passes, at `assets.py:1289`.
- Candidate selection — `assets.py:1120-1244`: candidates are silver posts that have **no current-prompt conformed row** (`assets.py:1184-1201`, `assets.py:1202-1224`); the in-flight guard at `assets.py:1224-1244` is the only thing preventing re-enqueue. A failed post (harvested with `ok=False`, therefore not conformed) **re-enters the candidate set on every drain run**.

Trace of the alleged scenario, once retry exists per ADR-0012 decision 5:

1. Post P fails at round 0: round-0 key materialized on both `submitted` and `harvested` → absent from the in-flight set (`partitions.py:236`). Its bronze landing is not conformed, so P reappears in candidates (`assets.py:1184-1224`).
2. A retry driver materializes a **round-1** key (`partition_key(w, 1, [P])`) on `enrichment_submitted` and submits to the provider (billed).
3. The drain runs again. `drain_suppressed_post_ids` tests only `partition_key(w, 0, [P])` (`assets.py:1060`). That key is in both `submitted` and `harvested`, so it is NOT in `submitted - harvested` (`partitions.py:236`). The round-1 key IS in the in-flight set, but the guard never constructs it.
4. Guard reports "not in flight" → P stays in candidates → `_materialize_submitted_partitions` re-adds the round-0 key (`assets.py:1289`) and P is enqueued into a new provider submit → **double-submit, double-bill**, while the round-1 retry is still running.

Caveat on liveness: **no code in the repo currently mints round N>0 keys.** The only callers of `partition_key` are `drain_suppressed_post_ids` and `_materialize_submitted_partitions`, both hardwired to `DRAIN_ATTEMPT_ROUND = 0` (`assets.py:1026,1060,1084`). Retry today still runs through the legacy queue (`batch.py:31-36` — `MAX_ATTEMPTS` explicitly marked "RETIRED with the queue... Kept only because analysis.py and harvest.py still import it while migrating"; `harvest.py:212-215, 247-260` route retries through `fail_item`/`dead_letter`). So the defect cannot fire today. But ADR-0012 decision 5 **mandates** that the future retry mechanism mint round-N keys ("Retry is a NEW partition key... Retry round N targets posts that have failed exactly N times" — ADR-0012 §Decision item 5), and `docs/architecture/pipelines/enrichment.md:388-390` repeats it. When that lands against this guard, the double-submit is deterministic, not hypothetical. The failure mode also matches the exact hazard decision 5 exists to prevent (re-billing provider work), just via the guard instead of the subtraction.

Verdict: **REAL — conditional on retry existing on the new key scheme, which is the design of record.** Not manufactured; the guard as written is only correct in a round-0-only world.

## 2. Structural-cause verdict: REAL

`in_flight_partitions` returns a `set[str]` of opaque 16-hex digests (`partitions.py:236`). The digest payload (`workload \0 round \0 sorted(ids)`, `partitions.py:155`) is not recoverable from the output: sha256 is one-way and the round/workload are inside the hash. The module's own docstring concedes this: "mapping an in-flight key BACK to a post id is impossible — the consumer re-derives `partition_key(workload, round, [pid])` per candidate and tests membership" (`partitions.py:83-87`), and `in_flight_partitions`' docstring repeats it (`partitions.py:212-214`). There is no scan-by-post primitive, and none can exist for this key shape: membership testing requires constructing the full key, i.e. knowing the round. Nothing in the drain's inputs tells it which round a candidate is at — the drain sees only `(workload, post_id)` and the lake. The structural cause stands.

## 3. Minimal interface change: option (a) — guard scans rounds `0..MAX_ATTEMPTS`

Options evaluated against the constraints: no ledger (ADR-0013: "The seam keeps no ledger table. There is no `external_jobs`"), in-flight is `materialized(submitted) − materialized(harvested)` (ADR-0012 decision 1), and both producer and consumer must derive the key from the same inputs.

**(a) Keep the key; guard scans rounds `0..MAX_ATTEMPT_ROUNDS`.** `drain_suppressed_post_ids` suppresses if ANY of `partition_key(w, r, [pid])` for `r in 0..MAX_ATTEMPTS` is in flight. Correctness: the in-flight set is round-agnostic (`partitions.py:236`), so scanning all constructible rounds recovers per-post answerability — at most one round of a post can be live at a time (a retry fires only after the previous round is terminal), so "any round in flight" ≡ "post in flight". Derivable by both sides: yes — the retry driver constructs `partition_key(w, N, [pid])` (it knows N); the drain constructs the full cross-product deterministically. No ledger: yes — `MAX_ATTEMPTS` is already a repo constant (`batch.py:31`, to be carried forward per ADR-0012 decision 6's "naturally bounded" phrasing). Cost: `MAX_ATTEMPTS+1` sha256s per candidate — trivial (~2.2k posts × 6 hashes). Cost: the retry bound becomes load-bearing in two modules; if it ever changes, in-flight keys from the old bound stay in the instance and remain visible (harmless — the scan only grows, never shrinks coverage). **This is the minimal change: one loop in `drain_suppressed_post_ids` and a shared `MAX_ATTEMPT_ROUNDS` constant in `partitions.py`.**

**(b) Per-post key without round; round carried elsewhere.** Rejected. ADR-0012 decision 5's reason for a NEW key is mechanical: "Because in-flight is a set difference, re-materializing an already-harvested partition is invisible and would orphan provider work (S3)" (ADR-0012 §Alternatives, "Re-materialize a partition to retry it: rejected"). A round-less key makes the retry key identical to the harvested round-0 key — re-materializing it lands in `submitted ∩ harvested`, vanishes from the subtraction, and orphans the provider job. That directly violates decision 5. Carrying round "as metadata" does not help: the in-flight set is keyed by the digest, and Dagster dynamic partitions have a single string key — there is no second dimension to put the round in without either a separate asset per round (an interface explosion, N assets × workloads) or a composite key that re-fuses the round anyway. Only version that could work — key = digest(workload, post_id) with round as a *prefix in the key string* — is just option (b)′: a non-digest, separable key. It is viable but strictly more invasive (every key comparison, docstring contract, and test changes; the drain and harvest both parse keys), for the same guarantee option (a) gives. Not minimal.

**(c) Status quo + "retries never co-exist with a live round-0 key".** Rejected as wishful thinking. The hazard scenario has round-0 **harvested**, not live — the convention is vacuous in exactly the case that matters. The only way to enforce non-coexistence would be to block retries while any round-0 key exists in the instance — but after harvest the round-0 key is not in flight, and there is no API to delete a dynamic partition's materialization history, so the "guard" would have to be a new derivation that reconstructs post identity it cannot recover (§2). Unenforceable.

**(d) Anything better?** Two candidates considered and rejected as inferior to (a):
- *Derive the round from the lake*: ADR-0012 decision 6 says "the landing table's row count per post IS the attempt count", so the guard could compute `round = count(landed rows for pid)` and test only that round's key. Rejected: it couples the guard to the bronze landing table (a new read dependency in the drain), and its correctness rests on every failure having landed a row — the same fragile invariant ADR-0012's own Consequences flag ("`bronze_enrichment_raw` cannot distinguish success from failure directly... an explicit status column is recommended"). A miscount silently tests the wrong round — a subtler version of the same bug.
- *Two-dimensional partitions / separate round asset*: heavier than the defect warrants (see (b)); Dagster dynamic partitions do not compose a second dimension cleanly.

**Recommendation: option (a).** It keeps the key derivable by both producer and consumer from the same inputs, keeps the in-flight set answerable per post (via bounded re-derivation), violates nothing in ADR-0013 (no new table, no stored state — the scan is a pure function of the instance snapshot and a constant), and preserves ADR-0012 decision 5's distinct-key-per-retry requirement. **No ADR amendment is required** — decision 5 mandates distinctness, not key shape (§5). What it does require is documentation: the drain's partition contract in `drain_suppressed_post_ids` (`assets.py:1048-1054`) and `enrichment.md`'s retry section should state that the guard is round-complete over `0..MAX_ATTEMPT_ROUNDS`, so the future retry implementer cannot assume round-0-only. That is a docs/spec change, not an architecture decision.

## 4. Are `account(...)` and `failure_set(...)` affected?

**`account` — YES, affected, two ways.** `account(instance, done=..., failed=..., backlog=..., total_candidates=...)` (`partitions.py:281-330`) takes `in_flight` from the instance as `len(in_flight_partitions(instance))` — a count of **keys**, spanning all rounds, not of posts.
1. *Under the buggy guard:* the double-submit of §1 materializes a second in-flight key for a post that already has one (round-0 re-added while round-1 lives) → `in_flight` over-counts → the identity `done + failed + in_flight + backlog == total_candidates` (`partitions.py:249-254`) breaks with a positive deficit. This is the guardrail doing its job — the accounting identity would actually *catch* the double-submit, but only as an unexplained deficit, not as a named defect.
2. *Even with guard (a) in place:* a post with a failed round-0 landing and a round-1 retry in flight is counted in `failed` (lake-derived: landed, not conformed) **and** in `in_flight` (instance-derived: round-1 key live) → double-counted → the identity breaks on every retry-in-flight. Fixing the guard does not fix `account`; `account` needs its state vocabulary sharpened — `failed` should mean **budget-exhausted terminal failure** (derived per ADR-0012 decision 6: `attempts >= MAX_ATTEMPTS`), not "any failed landing", so that a retrying post counts once, as in-flight. This is a semantic decision the retry slice must make explicitly; flag it in the retry workstream.

**`failure_set` — NO, not affected by rounds.** `failure_set(landed, conformed)` (`partitions.py:333-340`) is a pure anti-join over lake keys (`"p2@instagram"`-style, per `tests/unit/enrichment/test_partitions.py:296-301`) — it never sees partition keys or rounds. Under the §1 scenario it reports the retried post as failed-or-stuck continuously from its round-0 failure until its retry conforms. That is truthful (the post genuinely has no conformed row) and conservative: the blocking asset check (ADR-0012 decision 7) stays red while a retry is in flight, which is visible-but-noisy rather than wrong. No correctness defect; note the operator-facing consequence only.

## 5. What ADR-0012 decision 5 actually mandates

Quote (ADR-0012 §Decision, item 5):

> **5. Retry is a NEW partition key.** Because in-flight is a set difference, re-materializing an already-harvested partition is invisible and would orphan provider work (S3). Retry round N targets posts that have failed **exactly N** times — idempotent per round and naturally bounded.

The ADR mandates **distinct identity per retry round** — a NEW key, so the retry is visible to the subtraction and the budget is naturally bounded ("exactly N times", "idempotent per round"). It does **not** mandate the SHAPE — it never says the round must be hashed into an opaque digest with the post id, nor does it say anything about how a consumer maps keys back to posts. The key shape lives in `partitions.py`'s docstring ("Retry is a NEW key, deliberately: bumping `attempt_round` mints a fresh partition" — `partitions.py:73-76`) and in the drain's docstring (`assets.py:1027-1028`), both of which *cite* decision 5 but supply the fusion of round into the digest as their own design choice. Distinctness could, in principle, be satisfied by option (b)-style designs — but as argued in §3(b), the digest is what keeps the per-post derivability contract working under ADR-0013's no-ledger rule, and per-post derivability IS forced by ADR-0013 (the `partitions.py:33-36` reasoning: a per-batch key "would require the drain to consult the ledger we banned"). Within that constraint, keeping the round in the digest and making the guard round-complete (option a) is the minimal compliant design.

---

## Bottom line

- Mechanism: **REAL, conditional** — deterministic double-submit/double-bill once retry mints round-N keys; latent today (no round-N minter exists; legacy queue still carries retry).
- Structural cause: **REAL** — the digest is unscannable; the guard can only test fully constructed keys and nothing tells it the round.
- Minimal fix: **(a) round-complete guard** over `0..MAX_ATTEMPT_ROUNDS`; no ADR amendment; docs note required in `assets.py` guard docstring + `enrichment.md`.
- `account`: **affected** (needs `failed` redefined as budget-exhausted; identity otherwise double-counts retrying posts) — must be settled in the retry slice.
- `failure_set`: **not affected** (round-blind by construction; only operator-noise consequence).
- ADR-0012 decision 5 mandates retry-key **distinctness**, not round-in-digest; the fusion is a module-level design choice, and the guard's round-0 hardcoding is the hole it left.
