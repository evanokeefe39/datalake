The migration

Gold enrichment used to run in an external process (ADR-0002). That split coordination Dagster already owns out of Dagster, and it produced the #24 incident: an async Gemini batch finished on Google’s side while nothing polled or harvested it. The answer, ratified in ADR-0007/0008, is one orchestrated async path in Dagster.

Before — external worker
scripts/enrichment_worker.py
  • one-shot CLI — submit-then-poll cycle, then exits
  • nothing keeps it alive to poll async jobs to completion (#24)
  • batch claim + REST materialization lived in the process
  • interactive (sync) and batch both orchestrated by it
After — Dagster-native batch
gen_batches → media_upload → submit → harvest
  • harvest sensor is the persistent poller — #24 impossible by construction
  • submit + harvest are short bounded Dagster jobs; the hours-long work is external
  • interactive is out-of-band only (a manual script, never orchestrated)
  • defs/enrichment owns the logic; worker deleted

Not done — the cutover and the deferred tail

1 — Deploy and cut over (needs the live environment). The harvest sensor is DefaultSensorStatus.STOPPED by design until the smoke. Flipping it RUNNING, running a real submit → harvest at volume, and merging to main happen in the running Dagster, not on the branch.
2 — Strict interactive-vs-batch parity on the same posts. Not spent (structural parity only: same prompt hash / model / schema confirmed on the live apply).
3 — Job-6 residual retries. 2 tail items returned invalid JSON and are pending resubmission through the submit path — a real per-item retry, expected, not a stranded-terminal defect.
4 — Media-expiry race (cache bytes at scrape time). Pre-existing deferred direction (CDN URLs die in ~4–5 days); the media cache table exists and is populated (27,748 entries) but the scrape-time byte capture is not this migration’s scope.
5 — Batch-multimodal at scale + Tier-2 threshold. Batch now carries media via the File-API upload op; video-at-scale / batch-API-at-volume remains the follow-on that the plan always deferred to Tier-2 triggers.

What’s left, and the transferable lesson

The branch is the merge-ready deliverable. What happens next is deployment, not code.

  • Open the PR from migration/batch-native-enrichment to main, review, merge.
  • In the running Dagster: flip gemini_batch_harvest_sensor RUNNING; confirm a real submit → harvest run; let job-6’s 2 residual retries resubmit.
  • Then the follow-ons: scrape-time media-byte capture, batch-multimodal at volume, the Tier-2 threshold.

An async external job is not a one-shot synchronous fetch. If the answer comes back later as a handle, you need a poller that outlives any single run — and the guarantee that it exists is a sensor, not a process someone remembers to start. the #24 discipline, now enforced in Dagster
