Reading it

  • Everything inside the dashed box is the Dagster asset graph. It performs no Gemini calls. Network I/O is confined to the bronze ingestion assets (a download of media bytes into media_cache at scrape); silver onward is a pure transform.
  • The enrichment API calls live OUTSIDE the graph, in the standalone enrichment_worker: it claims queued items from ops.sqlite, uploads cached media to the Gemini File API, calls generate_content, writes gold_analyses, and posts an AssetMaterialization event. The DAG only ever enqueues and consumes gold — it never blocks on Gemini.
  • gold_analyses is an AssetSpec, externally materialized — it sits in the graph (so downstream serving views depend on it) but its writer is the worker, decoupled in time.
  • The async SQLite queue is the decoupling buffer between the transform graph and the stochastic, costly, rate-limited external producer.

Why this matters for what we discussed

  • Enrichment is already treated as an async external ingestion, not a transform — this is the seam that keeps Gemini calls out of the transformation layer.
  • Whole-corpus enrichment and Gemini batch API are execution-mode / discovery changes on the worker + enqueue side — they don’t move API calls back into the DAG.
  • Open questions under review: does the seam need to become a proper media-as-source + feature-store-style boundary as volume grows, or is the current worker + queue + AssetSpec the right shape?
